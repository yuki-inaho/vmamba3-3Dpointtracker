## 結論と完了範囲

実際のbest200重みから、標準ONNX演算だけのFP32 refinerを生成し、ONNX Runtime CPUとC++で実行する経路を整備しました。
C++版の推論にはPython、PyTorch、CUDAは不要です。Python版にも、学習環境とは分離した軽量なuv環境を用意しました。

**固定9動画・1,485フレームによる元のCUDA/BF16モデルとの精度比較は未実施です。したがって、作業全体のDoD達成、追跡精度維持、本番採用の判定はしていません。**
人工入力でのFP32同士の一致と、元のBF16モデルによる実データ精度は別の検証です。過去のmetric-AJ 24.7336%を今回の再測定値として扱いません。

## 重みと変換方針

提供PT：`tracker_mamba3_daoff_best200.pt`、32,490,569 bytes。
SHA256：`bcddf045311b76a91bc772e35901acbdb99f397b752ee0ba4beacb3fb1ded5f4`。
内部の `best_200.pt` のhashとは異なります。公開PTには50 tracker tensorsに加えてDINO前処理の2 bufferがあり、凍結backbone本体はありません。

変換時は50 tensorsをstrictに読み込み、key・shape・dtype・valueを照合します。Native側では、公開時に明示して除外された凍結DINO backbone全体だけを欠落許可の対象にします。
trackerやbufferの欠落、未知のkey、型・形状不一致、NaN/Inf、部分的なbackbone欠落は拒否します。PTは `weights_only=True` で読みます。

DINOは `facebook/dinov3-vits16-pretrain-lvd1689m`、revision `114c1379950215c8b35dfcd4e90a5c251dde0d32` に固定します。
公開PTにはflow設定がないため、paired評価では `--run-config configs/v64_official_mamba3_cache_phase.yaml` を明示します。SEA-RAFTへの暗黙の切替えはありません。

ONNXはopset 18、FP32、単一ファイルです。artifactのSHA256は `export_report.json` と同梱 `SHA256SUMS` に記録されます。
元のTriton学習経路やDAの式は変更せず、必要なDINO revision指定だけを任意引数として追加しました。

## 推論の入力・出力

**RGB動画を直接入れる一体モデルではありません。** DINO、WAFT、DA3は外部で計算し、次の8入力を渡します。
全入力はfloat32です。Bはバッチ数、Fはフレーム数、Nは追跡点数です。

| 名前 | 形状・意味 |
|---|---|
| `ray` | `(B,F,N,2)`、Kで正規化した視線 |
| `z_raw` | `(B,F,N)`、元のuvで取得した深度 |
| `visibility` | `(B,F,N)`、WAFTの0/1可視性。正解可視性やvis_headへ置き換えません。 |
| `uv` | `(B,F,N,2)`、896ピクセル座標系 |
| `depth_map` | `(B,F,Hd,Wd)`、メートル単位の深度 |
| `dino_features` | `(B,F,384,28,28)`、448入力のDINO特徴。学習対象のfeat_projより前。 |
| `intrinsics` | `(B,3,3)`、896画像へ合わせたK。歪み・skewなしの透視投影。 |
| `z_ref` | スカラー。**全B/F/Nをまとめたz_rawの下側中央値＋1e-6**。 |

出力は `xyz (B,F,N,3)`、`uv_refined (B,F,N,2)`、`vis_logits (B,F,N)`、`delta_uv (B,F,N,2)` です。
偶数個の中央値はNumPyの通常のmedianとは異なり、中央2値の小さい方です。点を分割する前に一度だけ計算します。
Python CLIはz_refが省略されている場合だけ、全入力から計算します。C++には検証済みのスカラーNPYを渡します。

標準演算による参照式はフレーム数に対してO(F²)のメモリを使います。分割できるのは点Nだけです。
フレームを分割して状態を捨てる変更は行いません。予算超過時はエラーになり、`--track-chunk` を小さくする必要があります。
メモリ予算の検査はattention作業領域の保守的な推定であり、特徴入力や実行環境を含む総RSSの上限保証ではありません。

## PythonによるCPU実行

以下はリポジトリrootから実行します。生成物は `result/onnx_best200_cpu/` に配置します。
同梱fixtureは実際の重みの動作確認用ですが、入力自体は人工データです。

```sh
uv sync --project deploy/onnx_cpu --locked --python 3.12
PYTHONPATH=src uv run --project deploy/onnx_cpu --locked python scripts/run_refiner_onnx.py \
  --onnx result/onnx_best200_cpu/tracker_mamba3_daoff_best200.onnx \
  --inputs result/onnx_best200_cpu/fixture/inputs.npz \
  --outputs result/onnx_best200_cpu/predictions.npz \
  --track-chunk 2 --threads 2 \
  --npy-directory result/onnx_best200_cpu/cpp_inputs
```

実入力に切り替える場合は、上記の8名の数値配列を持つNPZへ差し替えます。
型・形状・非有限値・可視性・K・z_refを入口で検査し、pickle/object配列は読みません。

## C++によるCPU実行

提供する実行例はLinux x86_64向けです。別OS／ABIは未検証で、配布バイナリがそのまま動くとは主張しません。
SDKは [ONNX Runtime v1.30.0](https://github.com/microsoft/onnxruntime/releases/tag/v1.30.0) の `onnxruntime-linux-x64-1.30.0.tgz` です。
SDK archive SHA256：`a5ed5a3cac51fbb2e90da632ae43d19212faaa20e76484e62bcb7c23ddb3b3fd`。

```sh
cmake -S cpp/refiner -B result/cpp_build -DCMAKE_BUILD_TYPE=Release \
  -DONNXRUNTIME_ROOT=/absolute/path/to/onnxruntime-linux-x64-1.30.0 \
  -DCMAKE_INSTALL_PREFIX="$PWD/result/cpp_runtime"
cmake --build result/cpp_build -j2
cmake --install result/cpp_build
result/cpp_runtime/bin/refiner_runner \
  result/onnx_best200_cpu/tracker_mamba3_daoff_best200.onnx \
  result/onnx_best200_cpu/fixture result/cpp_outputs 2 2
```

最後の数値は点分割数とスレッド数です。さらに作業領域予算MiBを任意で指定できます。
入力directoryに8個の `名前.npy` を置くと、4個の出力NPYと `SUCCESS.json` を書きます。終了コード0も必ず確認してください。
NPY v1/v2、little-endian float32、C順序の配列だけを受け付けます。
インストール先は `bin/` と `lib/` の相対配置を維持してください。MicrosoftのLICENSEとThirdPartyNoticesも同梱します。
このC++版はONNX Runtime C++ APIを利用しており、ggml版や独自SSMへ置き換えた実装ではありません。

## 品質検査と再変換

rootの学習・評価用依存は既存 `uv.lock` のままです。Python 3.12、PyTorch 2.12.1を含む環境で検査します。
最初のローカル試験には別のPython 3.13／PyTorch 2.10 CPU環境も使いましたが、それを作業書指定環境の代用結果とはしていません。

```sh
git submodule update --init --recursive third_party/visionMamba3
uv sync --locked --extra onnx --python 3.12
python3 scripts/validate_refiner_cpu.py \
  --ckpt /absolute/path/to/tracker_mamba3_daoff_best200.pt \
  --sdk-root /absolute/path/to/onnxruntime-linux-x64-1.30.0
```

このコマンドはrootのruff/ty/全pytest/lock、軽量環境のlock、actual best200のONNX生成、full checker、動的形状、
C++のコンパイルと実行、異常入力拒否、PyTorch未導入の独立プロセスでの照合を実施します。
元PTとroot lockのhashを検査前後で照合し、検証JSONを書きます。
GitHub Actionsの `.github/workflows/refiner-cpu.yml` でも同じコマンドを使用します。
ONNX、C++実行ファイル、fixtureはGitの追跡対象にはせず、配布物／Actions artifactへ保存します。

portable FP32対ONNX FP32の判定閾値は変更せず `rtol=2e-4, atol=5e-5` です。
B=1/2、F=1/8/13/128、Nと深度gridの変更、点分割1と一括を検査します。
C++は別seedでも10実行ケースと12異常入力ケースを検査します。公式参照式の単体試験にはF=257も含みます。

## 実データの最終判定

評価前の確認と実行は次のとおりです。元のGPU端末で、同一9動画・対応深度・WAFT重み・DINOアクセスが必要です。

```sh
source scripts/cudnn_env.sh
uv run --locked --extra onnx python scripts/eval_onnx_refiner.py \
  --ckpt /absolute/path/to/tracker_mamba3_daoff_best200.pt \
  --onnx result/onnx_best200_cpu/tracker_mamba3_daoff_best200.onnx \
  --run-config configs/v64_official_mamba3_cache_phase.yaml \
  --data-root "$HOME/data/tapvid3d" --depth-root "$HOME/data/tapvid3d_da3" \
  --out-dir result/onnx_best200_cpu/paired_reference --preflight-only
```

前提条件が揃った後の評価コマンドは同じ引数から `--preflight-only` を外します。
終了コード2は前提不足、1は評価失敗または採用条件未達、0はそのコマンドの成功です。
preflightだけの終了コード0は、精度合格を意味しません。精度判定は `comparison.json` の `acceptance_gate.passed` を確認します。

修正内容は、絶対metric-AJの算出、Kの256基準補正、公開PTの厳格読込、DINO revision固定、flow設定の明示です。
DINO特徴はnative実行で一度だけ取得し、その同じ配列をONNXへ渡します。flow可視性も共通です。
checkpoint hashとONNX metadataが異なる場合は比較を止めます。
9動画のmanifestはhash固定で、全1,485フレーム、failures0、同一membershipを要求します。
全体・各subsetでnativeが過去baselineのAJ/metric-AJと絶対差1e-6以内に一致し、ONNXの低下が0.001以内、OA差が1e-10以内であることを固定条件にしています。
XYZ・UVの可視点誤差分布とメートル誤差をsubset別に記録します。未実施・欠損・NaN・失敗・閾値超過は合格にしません。

既知のscore不具合2件の修正前失敗は [tdd_red_score.txt](evidence/onnx_best200_cpu/tdd_red_score.txt)、
回帰テストは `tests/unit/test_onnx_refiner_metrics.py` にあります。
本作業では以前のレビューで挙がった学習lossのNaN処理など、ONNX化以外の既存学習挙動は変更していません。

## 指定4参照先と選択理由（TR-6）

1. [HaoKun-Li/VMamba_onnx](https://github.com/HaoKun-Li/VMamba_onnx)：純粋なTorch演算化、scanの分解、ONNX生成・実行の比較方法を参照しました。
   対象は従来のVMambaであり、Mamba-3のRoPE・台形離散化を含む重みをそのまま読み込める実装とは扱っていません。
2. [MambaVision issue 110、2026-03-11の回答](https://github.com/NVlabs/MambaVision/issues/110#issuecomment-4042007183)：
   作者側の回答は、custom CUDA/Tritonのselective scanが標準exporterで扱えないという制約を述べています。
   元kernelをそのまま直接変換する経路には適用されますが、等価な標準演算へ展開した今回の経路まで不可能とする根拠にはしません。
3. [alxndrTL/mamba.py](https://github.com/alxndrTL/mamba.py)：純粋なPyTorch、parallel scan、ONNX実行の構成を参照しました。
   READMEのMamba/Mamba-2と今回のMamba-3は異なり、モデル・checkpoint互換の代替品にはしていません。
4. [ggml](https://github.com/ggml-org/ggml/blob/353b63b439f27ab2cc19dac97ab1681ba6d2d084/include/ggml.h)：`ggml_ssm_scan` 等のAPIはありますが、
   それだけでは今回のMamba-3固有計算、norm、GridSample、重み形式までの一致は保証されません。
   標準ONNXとC++実行経路が成立したため、追加演算と別の精度検証が必要なggml移植は採用していません。pixiへの環境移行も行っていません。

演算の直接照合元は [state-spaces/mamba](https://github.com/state-spaces/mamba/tree/e9594ce1c732d97440f0332fdc43170a2294dbfa) のMamba-3 moduleとSISO参照式です。
参照テストファイルのSHA256は `b68ec350f557a4124516f7d1c916ec756a48389fed4387791aadb74492531e85`、
moduleは `930c3dfa04dea8444b1c9ee8b6ac9cbbc7ef492dc5ae1f4c83051ef953eca33c` です。
C++実行は [ONNX Runtimeの公式C++ API](https://onnxruntime.ai/docs/get-started/with-cpp.html) に基づきます。
